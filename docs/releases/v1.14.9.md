# MeetingNotes 1.14.9

2026-10-09. Fixes periodic microphone dropouts introduced by the 1.14.0 capture
timeline change, particularly with larger/low-rate microphone buffers such as
those observed in an AirPods recording. GitHub publishes source and release
notes only; Apple Silicon installers are built locally.

## Microphone capture fix

- **Packet-aware output timing:** instead of always writing 120ms behind live
  input, the recorder accounts for the requested microphone buffer duration,
  actual converted frame counts and observed arrival latency. This prevents
  supported delayed microphone packets from being replaced with silence before
  their callbacks arrive.
- **Protect the first microphone buffer:** a bounded startup grace prevents
  fast system audio from committing silence while the first larger microphone
  packet is still filling. An absent microphone does not block system capture
  indefinitely.
- The shared 48kHz timeline, mic-only primary recording, original stem filenames,
  50/50 mix, genuine source pauses, source resumption and aligned Stop/finalization
  remain. Holdback is bounded to one second; PCM memory remains fixed at two
  seconds per source. Only write latency changes, not recording timestamps.
- The fix does not rewrite earlier audio. Speech already replaced with silence
  in a saved microphone/mixed track cannot be reconstructed by this update.

## Better capture diagnostics

The existing local log now retains sampled `recording:capture-timing` events:
microphone rate/channel count, requested and actual buffer sizes, callback age,
write holdback and late-frame counts. Events include first-packet metadata,
sampled updates and a Stop summary. Only allowlisted numeric metadata is retained;
device names, paths, arbitrary helper payloads and meeting content are excluded.
Logging failures cannot interrupt capture.

## Regression history

[PR #244](https://github.com/dbbaskette/MeetingNotes/pull/244), merged October 7
for 1.14.0, introduced the shared output clock to address
[mic-only capture and voice-stem reliability](https://github.com/dbbaskette/MeetingNotes/issues/173).
Its fixed 120ms window was shorter than the approximately 171ms buffer cadence
found in the reported AirPods recording. The native helper code was unchanged
through 1.14.8. The exact historical microphone sample rate/frame count was not
logged, but the periodic audio gaps and an offline reproduction support this
timing regression. It was not a transcript, summary or speaker-naming edit.

Earlier fidelity tests appended samples before output was drained, so they did
not model callback packets arriving only after their buffers filled. New tests
exercise that missing boundary. More details: [microphone timing](../microphone-timing.md).

## Verification

A full disposable clean-Mac run of `6909996` passed **1,343 tests (six skipped)**,
the complete Swift helper build, synthetic AAC/timeline/speech checks, types,
production build, docs, zero-warning repository lint, Browse benchmark and all
**10 synthetic UI fixture modes**. Environment: macOS 27.0 (26A428), Apple Silicon,
Node 22.23.2 and Electron 44.7.0. The runner deleted its test VM. Subsequent release
preparation changes only version metadata and documentation.

New native checks cover 48/44.1/24/16/8kHz-sized microphone packets, delivery
jitter, larger-than-requested first buffers, startup, mic-only capture, absent/
disabled mic, pause/resume and bounded late-input handling. Exact PCM preservation
is checked, and decoded AAC tone must contain signal in every interior 20ms
window—not merely have acceptable average volume. Timing logging tests verify
field filtering and failure isolation.

Synthetic tests do **not** establish real AirPods playback, Bluetooth device
switching, long-call drift or live-call acceptance. An arbitrarily late packet
still exceeds the bounded budget; already-written samples cannot be replayed.
Unexpected mid-call buffer growth may be learned only on arrival and is visible
in late-frame counters. Installer VM testing remains omitted by owner preference.
The local installer uses the existing **Apple Development** identity and is
**not notarized**. Requires macOS 14.2+ on Apple Silicon.

## Upgrade and what to check

No new database migration, setting or recording-file relocation is added since
[1.14.8](https://github.com/dbbaskette/MeetingNotes/releases/tag/v1.14.8). Existing
Library/settings and recordings are preserved. Building the installer does not
install it or interrupt an active recording. Finish active work and quit
MeetingNotes before replacing the app; keep a complete Library backup.

After installing, verify **1.14.9**, select AirPods as the Mac's microphone and
use **Settings → Setup & health → Test recording…**. Speak continuously and play
the short test back, then check a short normal call. Listen for repeated pumping/
cuts, compare mic/mixed playback, and retain audio/logs if the problem persists.
`recording:capture-timing` shows actual buffer timing and late-frame counts.
Switching input devices mid-recording needs separate hardware verification.

Rolling back to 1.14.8 reintroduces this capture defect; it adds no new migration
relative to this patch. Downgrading farther may have the encrypted-secret/template
compatibility limitations documented in the 1.14.8 notes. Do not assume an app
downgrade reverses earlier data changes.
